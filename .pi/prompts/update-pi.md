Coordinate a Pi update from this repository. Do not update the installed Pi until extension compatibility checks pass.

1. Read the current `@earendil-works/*` pins in `package.json`, the installed `pi --version`, and the Pi input in `~/dev/dotfiles/home/.config/home-manager/flake.nix`. Inspect both repositories' working trees and preserve unrelated changes. Never stash, revert, or overwrite unrelated changes. Before activation, check whether unrelated Home Manager changes are already applied. If this cannot be established, ask permission before activating them.
2. Query the latest stable `@earendil-works/pi-coding-agent` release with `sandbox pnpm view @earendil-works/pi-coding-agent version`. If the dependency pins, installed version, and dotfiles input already match it, report that no update is needed.
3. Read the target release's `packages/coding-agent/CHANGELOG.md` on GitHub for every release after the oldest current version through the target. Compare relevant changes against `extensions/` and report breaking changes, deprecated APIs we use, and new APIs that could simplify or fix our extensions. Read the target release's relevant API documentation before making compatibility changes. Stop and discuss blockers before proceeding.
4. Pin `@earendil-works/pi-ai`, `@earendil-works/pi-coding-agent`, and `@earendil-works/pi-tui` to the exact target with `sandbox pnpm add --save-dev --save-exact`. Run `just check` and fix compatibility failures only. Report unrelated failures without hiding them. Do not proceed while checks fail.
5. Read the dotfiles instructions and update recipes. Recheck the latest release before installation; if it differs from the tested target, stop and review that release first. Run `just pi-update` from `~/dev/dotfiles` using its own development shell and sandbox tooling. Do not use this repository's sandbox for dotfiles commands. Confirm the resulting Pi input and installed `pi --version` match the tested target. If the recipe skips applying an already-pinned version while the installed version is older, use the documented dotfiles apply recipe. Allow at least 20 minutes for Nix builds. If the update is interrupted after pinning the target, inspect the logs and installed version, then use the documented dotfiles apply recipe to finish. Check activation logs as well as the exit status. Report build or activation failures clearly, and report unrelated service failures separately.
6. Summarize compatibility changes, check results, and the installed version. Tell the user to restart Pi after an installed update. When concrete, useful API adoption opportunities are identified, propose them as phases in PLAN.md using the plan-md skill, and discuss them before implementing. Otherwise, state that none were found and do not add phases. Do not commit unless asked.
